# 5.0.0 — the breaking changes, enumerated

**This file exists for the same reason `4.0.0-breaking-changes.md` does.** The
work since 4.0.0 is three cycles: "One act, one answer" (five filed bounty and
astrolabe bugs), "Data you can't get back" (bounty and astrolabe data loss) and
"Scriptorium from real use, round two" (toasts and markdown chat). Every commit
was typed `feat` or `fix` with no `!` and no `BREAKING CHANGE:` footer, so
release-please would cut a minor for a release in which six invocations that
exited 0 now refuse, a command that exited 5 now exits 0, and two that hung now
exit 1.

⚠ **EVERY ENTRY BELOW WAS OBSERVED, NOT COPIED.** The population was every
`feat` and `fix` commit in `git log spellbook-v4.0.0..develop --no-merges` (27
`fix`, 2 `feat`) and the release-note tables in the three cycle docs' Outcome
sections. Each claim was re-run against the shipped 4.0.0 build (tag
`spellbook-v4.0.0`, its committed `dist/`) and against `develop` at `b34d9db4`,
through the same launcher
(`bun plugins/spellbook/skills/<spell>/scripts/cli.ts …`), in a throwaway
`HOME`, `TMPDIR`, `BOUNTY_HOME` and `ASTROLABE_HOME`. Unreadable files were made
by writing invalid JSON, by putting a directory where a file goes, by
`chmod 555` on the parent, and by `chflags uchg`. Some cycle-doc claims were
incomplete (see the end). Enumerated at `b34d9db4`: **fifteen breaking
changes**: four exit codes, seven refused invocations, one changed field, one
timing change and two behaviour changes. That count excludes the "Not breaking"
section below. Where a count and a list disagree, trust the list.

## How failures look now

Unchanged from 4.0.0: stdout is empty and stderr carries one JSON document on
one line, `{"ok":false,"error":{"kind",…,"exit_code",…},"meta":{"command"}}`,
with `2` usage, `1` internal, `5` not_found and `6` conflict (see
`4.0.0-breaking-changes.md`). Route on `kind`, the exit code and `choices`,
never on `message`. Two things are new on the failure envelope this release:

- bounty's `conflict` refusals from the daemon carry its reply verbatim under
  `error.server` (`init` over tasks, `close` whose save failed).
- The data-loss refusals put the recovery in `hint` as a command you can run as
  printed (`open --session-key K --fresh --restore <file> --no-open`), and name
  the file path in `message`.

## Exit codes

1. **bounty `init --stdin-tasks` over a board that has tasks: 0 → 6.** Before:
   `{"ok":true,"sent":"init","tasksDropped":null}`, exit 0, and every task on
   the board was replaced. Any JSON array does this, `[]` included, which
   emptied the board. Now: `conflict`, exit **6**, the board unchanged, and the
   hint names `--replace`. Seeding an empty board answers as before. Why: `init`
   silently wiped a live board.
2. **bounty `close` whose final save fails: 0 → 6.** Before: with the snapshot
   path unwritable (a directory in its place, or no write permission), `close`
   answered `{"ok":true,"sent":"close","down":true}` and the board was saved
   nowhere. Now it exits **6** (`conflict`) in one of two forms:
   - the board was dumped to `<id>.unsaved-<ts>.json` (in `snapshots/`, or in
     `$BOUNTY_HOME` when `snapshots/` is the problem). The board is down, and
     the hint names the path to fix and the restore command.
   - nothing could be written anywhere. The close is refused and **the board
     keeps running**, because it holds the only copy. Close again once a path is
     writable.

   Why: a success exit over a board in no file was a silent loss.

3. **bounty `tail --session-key <key>` on a board that has closed: 5 → 0.**
   Before: retry lines on stderr for about 8 seconds, then `not_found`, exit 5.
   Now: one `tail.closed` line on **stdout** at once, exit **0**, whose
   `command` is `open --session-key <key> --no-open`. It now matches
   `tail --session <id>`, which already did this. A key with no board and no
   snapshot still exits 5 after the grace. A script that treated 5 as "that
   board is over" must now read the `tail.closed` frame.
4. **astrolabe verbs naming a project, with no daemon up and an unreadable
   `registry.json`: 2 → 6.** This covers `status`, `attention`, `poke`, `remove`
   and `join`. Before: `usage`, exit 2, "unknown project" (the registry was read
   as empty), and a daemon was spawned. Now: `conflict`, exit **6**. The message
   names the file and why it can't be read, the hint gives the two ways forward
   (repair it, or `open` to set it aside), and nothing is spawned or moved. Why:
   "unknown project" was false; the registry was not empty, it was unreadable.

## Refused invocations

Each of these used to succeed at exit 0 and is now refused, with nothing written
or started.

5. **bounty `open --restore <id>` with no such snapshot: 0 → 5.** Before: an
   empty board was started and left running, with `restoreFailed` set to the
   `ENOENT`. Now: `not_found`, exit **5**, and the hint names `sessions`. No
   daemon is spawned and, under `--fresh`, no live board is torn down. A
   snapshot that exists but is damaged still starts a board and reports
   `restoreFailed`.
6. **bounty `open --restore ""`: 0 → 2.** Before: a fresh empty board,
   `restoreFailed: null`. Now: `usage`, exit **2**, nothing started.
7. **bounty `add <title> --stdin`: 0 → 2.** Before: the stdin text became the
   title and the positional was dropped. Now: `usage`, exit **2**, nothing
   added. Pass one or the other.
8. **bounty `message <text> --stdin`: 0 → 2.** The same shape: the stdin text
   was sent and the positional was dropped. Now: `usage`, exit **2**, nothing
   sent.
9. **astrolabe `add` with no daemon up and an unreadable `registry.json`: 0
   → 6.** Before: it spawned a daemon that read the registry as empty, added the
   project, and overwrote the file on its next save, so every registered project
   was lost. Now: `conflict`, exit **6**, nothing spawned or written.
10. **astrolabe `open` when an unreadable `registry.json` cannot be set aside: 0
    → 1.** Before: with the file immutable (`chflags uchg`), `open` booted an
    empty board, exit 0. Now: the daemon will not start over the bytes, and
    `open` fails at once with `internal`, exit **1**, giving the OS error for
    the failed rename. The daemon's own line is under `error.server`. (When the
    rename works, `open` succeeds and the file is set aside; see "Not
    breaking".)
11. **bounty `open` when the id's lock is held by a live pid it cannot check: 0
    → 6.** Every board id now has a lock at `$BOUNTY_HOME/locks/<id>.lock`. If
    that lock names a live pid and `ps` cannot be run to tell whether the pid is
    this board's daemon, `open` refuses: `conflict`, exit **6**. The envelope
    names the lock, the pid and the reason, and nothing is spawned. 4.0.0 had no
    lock and spawned a daemon. Observed with a hand-written lock naming a live
    `sleep` and `PATH=/usr/bin` (macOS keeps `ps` in `/bin`). Why: two daemons
    for one id wrote over each other's snapshots.

## Changed field meaning

12. **bounty `restoreFailed` is set for a snapshot whose `tasks` is not an
    array.** Before: `open --restore <id>` of `{"title":"t","tasks":"x"}`
    reported `restoreFailed: null` and took the snapshot's title (`"t"`). Now
    `restoreFailed` is `{path, reason}`, the reason reading "the snapshot's
    `tasks` is not an array (string)", and the board keeps the default title.
    The same applies to a non-object snapshot and to a missing `tasks`. Why: a
    null `restoreFailed` told the caller an empty board was the snapshot.

## Timing

13. **bounty `open` and `close` on a daemon that is not answering: hang →
    exit 1.** Before: against a SIGSTOPped daemon, both were still running when
    stopped at 12 s. Now each request to the daemon gives up after 2 s: `close`
    exits **1** (`internal`) after about 2 s, and `open` exits **1** after about
    9 s ("held by a running daemon (pid N) that is not answering"). Both hints
    say to resume or end that pid. Requests from `add`, `update`, `claim`,
    `block`, `unblock`, `remove`, `message`, `init` and `state` are still
    unbounded.

## Behaviour

14. **bounty `open --session-key K --fresh --restore <K's own id>` restores the
    snapshot, not the live board.** Before: the teardown's `close` wrote the
    live board over K's snapshot and the new board restored that write. With a
    task added just before the call, the result had 2 tasks. Now the snapshot is
    copied to `<id>.pre-fresh-<ts>.bak.json` before the teardown and the board
    is restored from the copy: 1 task. The live board is kept too, as a
    `pre-restore` backup, and both are named on `snapshotBackups`. A caller that
    used this call to "restart and keep what's live" gets the snapshot instead.
15. **bounty's idle timeout does not end a board that is in no file.** With
    nothing writable, 4.0.0 ended the daemon at the idle timeout (`--timeout 3`:
    gone within 10 s) and its tasks were lost. Now the timeout is held while no
    save works: the daemon keeps running, `state.snapshotSaveFailed.held` gives
    the reason, and the save is retried each time the timeout comes round. The
    board ends as a normal timeout (124) once a save works. SIGTERM and SIGINT
    still stop it.

## Not breaking, and worth saying so

- **Newly accepted:** bounty `init --stdin-tasks --replace` (the reply gains
  `tasksReplaced: <n>`, never null); `--replace` without `--stdin-tasks` is
  refused at exit 2. `init`'s `choices` and `schema` gain `--replace`.
  `tasksDropped` keeps its meaning: the caller's input entries that were
  rejected.
- **Additive fields:**
  - bounty `open` and `close` gain `snapshotBackups` (present and `[]` when
    nothing was backed up). Each entry has `kind` (`pre-fresh`, `pre-restore`,
    `unreadable`, `unread`, `shrink` or `unsaved`), `path`, `taskCount`,
    `reason` and `restore`. `restore` is `null` for a file that cannot be
    restored as it stands, or for a superseded `unsaved` dump.
  - bounty `state` gains `snapshotSaveFailed` (null once a write succeeds), and
    the tail gains a `snapshotSaveFailed` event.
  - astrolabe `info`, `state` and `list` gain
    `registry_set_aside: [{path, recover}]` while a set-aside registry exists.
  - astrolabe's cold unknown-project refusal gains `hint` and `choices` (the
    registered ids; `[]` for an empty registry). 4.0.0 had neither.
  - The daemon's unknown-project rejection carries
    `reason: "unknown-project", project`.
- **Same exit, nothing started:** an astrolabe `status`, `attention`, `poke`,
  `remove` or `join` naming an unknown id, and a duplicate `add`, still exit 2
  `usage` with no daemon up. They no longer spawn one.
- **astrolabe sets an unreadable registry aside.** A daemon that boots over an
  unreadable `registry.json` renames it to `registry.json.unreadable-<time>` and
  starts empty. It no longer reads it as empty and saves over it later. Every
  success then prints a `# warning:` line on stderr until the file is dealt
  with; stdout and the exit code are unchanged.
- **astrolabe `open` fails fast when the daemon cannot start.** For example,
  with an unwritable `$ASTROLABE_HOME` it still exits 1 `internal`, but at once
  and in the daemon's own words, where 4.0.0 waited 45 s and said "failed to
  start".
- **One bounty daemon per id.** Two concurrent `open --session-key K` both exit
  0 and report the same board, as before. 4.0.0 left two daemons running for
  that id; now one runs, and the other `open` prints a
  `# another open started board … first; attached` line on stderr.
- **New files in `$BOUNTY_HOME`:** `locks/<id>.lock`, and backups in
  `snapshots/` (`*.pre-fresh-*.bak.json`, `*.pre-restore-*.bak.json`,
  `*.unreadable-*.bak.json`, `*.unread-*.bak.json`, `*.unsaved-*.json`). Like
  any `.json` there, they are listed by `sessions`. Snapshot writes are atomic
  (tmp + rename).
- **An unreadable bounty snapshot is copied aside** before anything is written
  over it. `restoreFailed` is the same as in 4.0.0; `snapshotBackups` names the
  copy.
- **Message wording** changed on the refusals above and on
  `tail --session-key`'s `not_found` hint. Same exit, same `kind`.
- **scriptorium:** new-version toasts with Activate and Show diff, toasts drawn
  at the bottom of the document pane, and `say` text rendered as markdown in the
  chat. These are surface changes with no CLI or JSON change (no scriptorium
  backend file changed). An agent's `say` containing markdown syntax now shows
  rendered to the human, and raw HTML shows as text. SKILL.md no longer asks the
  agent to announce a new version in chat.

## Claimed in the cycle docs, and corrected here

- **"astrolabe commands naming a project: exit 6 `conflict` on an unreadable
  registry (was 2 `usage`)"** is true of `status`, `attention`, `poke`, `remove`
  and `join` (entry 4), and only with no daemon up. `add`, which names no
  project id, was **0**, not 2 (entry 9). Once a daemon is up, the registry has
  been set aside, and an unknown id is still 2 `usage`.
- **"astrolabe `open` … exit 1 if it cannot [set it aside]"** gives no "before".
  It was 0 when the file was immutable (entry 10), and 1 after 45 s when
  `$ASTROLABE_HOME` was unwritable (not breaking).
- **"bounty `open` / `close` on a stopped daemon: exit 1 after a bound"**: the
  bound is 2 s per request, but `open` makes several and took about 9 s in all.
  `close` took about 2 s.
- **"bounty `open` with lock liveness unknown: exit 6"**: the commit gives the
  "before" as a raw Bun stack at exit 1. That was the state between two commits
  of the same cycle (`10d830ee` and `f7f80871`), not 4.0.0, which had no lock
  and exited 0 (entry 11).
- **Missing from the cycle tables:** entries 9 to 12, 14 and 15, and the
  additive `tasksReplaced`, the `snapshotSaveFailed` event and astrolabe's new
  `hint`/`choices`.

## Not verified

- scriptorium's toasts and markdown chat were not driven in a browser here. The
  claim that no CLI or JSON output changed rests on the diff: only
  `src/scriptorium/surface/` and SKILL.md changed.
- The `unread` and `shrink` backup kinds and the "superseded `unsaved` dump"
  (`restore: null`) path were not reproduced. They are additive, and entries
  above do not depend on them.
- The daemon's `reason: "unknown-project"` was read from the code
  (`src/astrolabe/backend/cli.ts:392`), not seen on the wire.
